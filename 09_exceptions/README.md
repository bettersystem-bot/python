# 09 异常传播与失败策略

## 这一章为什么要补

前面的章节已经讲了“怎么并发跑起来”，但真实项目里更常见的问题是：并发任务里有人失败了，整个程序应该怎么办？

异步异常最容易让初学者困惑，因为失败不一定发生在你创建任务的那一行，而是发生在未来某个 `await` 恢复的时候。

可以把它想象成点外卖：你同时下了 3 单。下单时都成功了，但 20 分钟后其中一家店突然取消订单。真正需要处理问题的，不是“下单那一刻”，而是“你等结果那一刻”。

## 这一章学什么

你会学到：

- `gather` 遇到异常时的默认行为
- `return_exceptions=True` 什么时候有用
- 为什么后台任务必须有人负责收尸
- `asyncio.shield()` 如何保护关键任务不被外层取消
- 如何把失败结果收集起来，而不是让异常四处乱飞

## `gather` 的两种失败策略

默认策略：一个任务抛异常，`gather` 会把这个异常抛给调用方。

一个容易误解的细节是：`gather` 把异常抛给调用方，不等于所有兄弟任务都一定已经停止。

如果这些任务已经被调度运行，某些还没完成的任务可能会继续跑一小段时间。真实项目里如果需要“一个失败，全部停止”，通常要自己保存任务对象并明确取消剩余任务。

容错策略：设置 `return_exceptions=True` 后，异常会作为结果列表中的一个元素返回。

它们分别适合不同场景：

- 默认策略适合“任何一个失败都应该整体失败”的任务
- 容错策略适合“批量处理，允许部分失败”的任务

## 为什么要关注后台任务异常

如果你 `create_task()` 之后既不 `await`，也不保存引用，任务失败时很容易变成“没人处理的异常”。

好的习惯是：

- 要么最终 `await task`
- 要么用回调集中记录异常
- 要么把任务交给一个明确的任务管理结构

## 运行方式

```bash
python3.10 09_exceptions/exception_strategies.py
```

## 练习建议

- 修改哪个任务会失败
- 把 `return_exceptions=True` 改掉观察区别
- 删除后台任务的回调，看控制台有什么变化
- 尝试给关键任务加取消保护
