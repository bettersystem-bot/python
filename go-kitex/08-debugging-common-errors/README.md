# 08 常见错误与排查路径

## 学习目标

- 区分生成期、启动期、调用期问题。
- 掌握超时、连接失败、IDL 不匹配、版本差异的排查顺序。
- 即使无法本地运行，也能通过阅读代码完成学习。

## 总体排查顺序

```text
1. 错误发生在哪个阶段？生成期 / 启动期 / 调用期
2. 错误是业务错误还是 RPC 框架错误？
3. 请求有没有到达 Server？
4. Client 和 Server 是否使用同一份 IDL / 生成代码？
5. 超时、重试、地址、服务发现配置是否正确？
6. 日志、trace、关键请求字段是否足够定位？
```

## 生成代码失败

检查：

- `kitex -version` 是否为内部 `v1.x.x`。
- `thriftgo --version` 是否可用。
- `go.mod` module 名称是否和 `-module` 一致。
- IDL include 路径是否正确。
- 是否把 Thrift 语法写成 Go 语法。
- 是否有内部仓库 / 公共 IDL 访问权限。

## IDL 改了但代码没生效

常见原因：

- 忘记重新执行 `kitex ...`。
- 改了另一份 IDL 文件，不是当前生成命令使用的文件。
- Client 和 Server 依赖的生成代码版本不一致。
- 手动改了 `kitex_gen`，下一次生成被覆盖。

处理：重新生成代码，检查 diff，确认调用方和服务方使用同一份契约。

## 本地无法启动服务

检查：

- 端口 `127.0.0.1:8888` 是否被占用。
- `main.go` 是否使用正确的 Handler。
- Handler 方法签名是否与生成接口一致。
- 依赖是否完整拉取。
- 是否在正确 Go module 目录下运行。

## 调用超时

先判断：

- Client 是否连到了正确地址。
- Server 是否真的启动并监听目标端口。
- Handler 是否阻塞或耗时过长。
- `WithRPCTimeout` 是否设置过小。
- 是否开启重试导致总耗时更长。

日志中建议带上：方法名、request id、超时时间、实际耗时、目标服务名或地址。

## 业务错误 vs 框架错误

- 业务错误：参数非法、资源不存在、状态冲突。通常由 Handler 主动返回或通过响应里的业务状态表达。
- 框架错误：超时、连接失败、服务不可用、序列化失败、ACL 拒绝等。通常发生在 RPC 框架或网络层。

不要把所有错误都包装成“系统异常”。先分类，再决定是否重试、告警或返回给上游。

## 公司内部版本和网上教程不一致

处理原则：

1. 以公司内部 Kitex Tool `v1.x.x` 和内部文档为准。
2. 优先参考同业务线现有服务代码。
3. 不确定 API 是否可用时，先在练习 module 中最小化验证。
4. 不要为了匹配网上教程随意升级生产依赖。

## 无法本地运行时怎么学

可以做这些只读练习：

- 画出一个接口从 IDL 到 Handler 再到 Client 的调用链。
- 标注 Request / Response 每个字段的编号、类型、是否 optional。
- 找出业务逻辑所在 Handler，解释每个错误返回的含义。
- 阅读 Client 初始化，指出超时、重试、服务发现、负载均衡配置在哪里。
- 按本章排查顺序解释一个超时错误可能来自哪里。
